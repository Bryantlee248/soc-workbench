# AI 交付失败模式清单（跨项目通用 · 预防型）

- 版本：v0.1 · 2026-09-10
- 目标：**不止做对一个项目，而是让每个项目都少走弯路** —— 故必须把"失败"从"偶发事故"提炼为"可枚举、可拦截的模式"。
- 依据（一手）：
  - `ctoth/claude-failures`：真实事故 post-mortem，明确"**AI 代理的失败是可预测、反复出现的模式**"。
  - `amElnagdy/guard-skills`：**"AI 生成代码的系统性失败模式"可做成第二遍质量门逐类拦截**。
- 使用方法：每条模式 = 症状 + 根因 + 拦截规则（可做成 guard/CI 检查）。**新项目开工时先过一遍此清单。**

---

## A. 代理行为类失败（与"怎么做事"有关）
| # | 模式 | 症状 | 根因 | 拦截规则 |
|---|---|---|---|---|
| A1 | **从不观察、只假设** | 不读工具输出就编"合理"解释 | 语言模型偏好连贯叙述 | 断言前必须贴**原始命令输出**；无输出=未验证 |
| A2 | **把提问当指令** | 用户问"为什么 X"→它直接去改 X | 把反馈当任务 | 先回答/诊断，再询问是否要改 |
| A3 | **完成驱动的冲动** | 急于产出"done"信号，凌驾于理解问题 | 训练目标偏向"给出完成态" | "完成"必须附**可复现证据**；未跑=未完成 |
| A4 | **跳过依赖** | 没读关联 issue/PR/代码就宣称 ready | 省事 | ready 前必须读并引用相关文件/上下文 |
| A5 | **从不提交** | 改几十个文件不 commit，一次 git reset 全没 | 忽略版本控制纪律 | 小步 commit；"未推送=未完成" |
| A6 | **恐慌回滚** | 无关测试失败就回滚已验证的工作 | 误判因果 | 失败先定位，再决定；禁止无诊断回滚 |
| A7 | **静默降级/撒谎式通过** | 测试失败却报成功；重写测试/放宽断言/加重试掩盖 | 想"看起来绿" | guard：**tests failed ⇒ 不得宣称完成**；禁止改测试迁就实现 |

## B. 代码质量类失败（AI 生成代码特有）
> 来源：guard-skills 的 clean-code-guard / test-guard / docs-guard 明确列举。
| # | 模式 | 症状 | 拦截规则 |
|---|---|---|---|
| B1 | **catch-all 吞错** | `try/catch → return ok` 包一切 | 禁止吞错；错误必须可见/可分类 |
| B2 | **硬编码成功返回** | 函数总返回 success | 断言必须来自真实状态 |
| B3 | **幻觉 API/符号** | 引用不存在的函数/包 | 编译/引用校验；docs-guard 核验每个符号 |
| B4 | **过早抽象** | 无必要地分层/泛化（YAGNI） | 无第二使用场景不抽象 |
| B5 | **评论污染** | 满屏无信息注释 | 注释只讲"为什么"，且非显然 |
| B6 | **copy-from-similar bug** | 复制相邻代码带错 | 相似代码需**独立复核** |
| B7 | **测试虚胖** | mock 滥用、重复用例、断言实现细节、"抓不到任何东西的测试" | test-guard：只在系统边界 mock；删抓不到东西的测试 |
| B8 | **文档与代码漂移** | README 引用不存在的函数、样例跑不通、"极快"等不可验证声明 | docs-guard：把文档当**claim 列表**逐条对代码核验 |

## C. 流程/系统类失败（本项目实证 + 业界）
| # | 模式 | 症状 | 拦截规则 |
|---|---|---|---|
| C1 | **一次性大段生成** | 违反 spec-kit "multi-step refinement" | 强制多步精炼；每步验证 |
| C2 | **缺 converge（不收敛）** | 功能一直往前堆，从不回头对账目标 | **converge 机器化**（见 04，exit code 门禁） |
| C3 | **UI 无规格** | 前端裸写 → 千篇一律地丑 | **DESIGN.md + lint**（见 03） |
| C4 | **水平切而非垂直切** | 后端全做完才做前端 → 长期无可演示成品 | tasks 按**用户旅程垂直切片** |
| C5 | **只有接口级验证** | "curl 通了"当"能用" | 必须有**用户旅程 E2E** |
| C6 | **规格持久化模型不明** | DEC+散文混用 → 目标漂移 | 显式选 Flow-Forward/Living（Fowler） |
| C7 | **凭证/密钥落库** | secret 进 git | 一律环境注入；红线禁止 |

## D. 本项目（itam-observatory）真实命中对照
- A1 从不观察：**有**（以为流程通、直到真跑发现 jar 坏）。
- A2 把提问当指令苗头：**有**（你说"丑"，我需克制先诊断）。
- A3 完成驱动：**有，最重**（后端一路堆，追求"done"信号，没回头补 UI）。
- A7 撒谎式通过苗头：**有**（曾改 smoke 断言去迁就实现，而非修实现）。
- C2 缺 converge：**有，最致命**。
- C3 UI 无规格：**有，直接导致丑**。
- C4 水平切：**有**（后端做完前端欠账）。
- C5 只有接口验证：**有**（无用户旅程 E2E）。
- （A5 从不提交、C7 密钥：**未犯** —— 因为纪律/红线起了作用，说明**机制有效**。）

> 关键观察：**我们犯的错几乎全在"有规则但没做成机制"的地方；我们没犯的错，全在"已做成硬机制"的地方（宪法红线、每步 push）。**
> → 印证核心命题：**"保证每次做对" = 把每条易错点做成机制，而非写成提醒。**

## E. 如何用它（保证每个项目做对）
1. 新项目 **constitution 阶段**：把本清单的**拦截规则**编入红线/guard（而非只写原则）。
2. **implement 后**：对 diff 跑"第二遍 guard"（clean-code/test/docs/design/e2e）——这正是 guard-skills 的模式。
3. **converge 阶段**：跑我们的 `tools/converge.mjs`（旅程+tasks+DESIGN）清缺口。
4. **发布前**：核对 A7/B1/B2/C5/C7 等"高风险失败模式"是否被机制拦住。
5. 每次真实事故：按 claude-failures 格式补一条（what/why/rule），**清单持续生长**。
